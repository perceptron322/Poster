## Итоги и обнаруженные ограничения

В ходе практических экспериментов на тестовом HA-стенде проверены работа PostgreSQL primary-replica, поведение узлов при остановке и восстановлении, а также резервное копирование и восстановление базы данных.

**Основные результаты:**
- Подтверждена работа физической асинхронной репликации PostgreSQL: состояние соединения — `streaming`, функция `pg_is_in_recovery()` на replica возвращает `true`.
- Проверено распространение записей с primary на replica и отклонение попыток записи непосредственно на реплике.
- При остановке replica primary продолжил принимать записи. После запуска репликация восстановилась.
- При остановке primary ранее реплицированные данные оставались доступны для чтения на replica. После запуска primary репликация возобновилась автоматически.
- Резервная копия `course_app.dump` успешно создана и восстановлена в отдельную базу `course_app_restored`. Проверены контрольные записи и ограничения таблицы.

Дополнительно на HA-стенде проверена отдельная база `poster_ha`: применены миграции проекта, подтверждено наличие семи таблиц на primary и replica, проверена репликация операций добавления и удаления пользователя, а также работа ограничения уникальности email. Проверки выполнялись напрямую через SQL, без запуска HTTP API приложения.

**Обнаруженные ограничения:**
- Репликация работает в асинхронном режиме (`async`), поэтому при аварийном отказе primary возможна потеря последних изменений, ещё не переданных на replica.
- Автоматическое переключение replica в primary не настроено. При отказе primary для восстановления записи требуется дополнительное переключение ролей.

**Заключение:** практические испытания подтвердили работоспособность репликации, восстановление соединения после остановки узлов и возможность резервного копирования и восстановления. Для полноценной отказоустойчивости необходимы механизм переключения ролей и расширенные проверки целостности данных.
