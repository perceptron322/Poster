# Оптимизация MongoDB-запросов

Эксперимент покрывает ровно два запроса:

1. **Каталог мероприятий** (`event_catalog`): равенство по `event.type` с сортировкой по `event.starts_at`. Индекс `{ event.type: 1, event.starts_at: 1 }` обслуживает фильтр и сортировку.
2. **Мероприятия исполнителя** (`performer_events`): поиск по `performer_ids` с сортировкой по `event.starts_at`. Multikey-индекс `{ performer_ids: 1, event.starts_at: 1 }` обслуживает ссылку на исполнителя и порядок выдачи.

## Запуск и методика

На заполненной MongoDB проекта выполнить из корня репозитория. Фильтры строятся из существующего документа, поэтому не зависят от конкретных типов мероприятий или наличия отзывов.

```bash
scripts/mongo/optimization/run.sh
```

Скрипт временно удаляет два исследуемых индекса, чтобы зафиксировать базовые планы без них, затем выполняет по умолчанию 2 прогревочных и 11 измеряемых запусков каждого запроса, создаёт целевые индексы и повторяет замеры. Исходные индексы восстанавливаются в конце. Для изменения числа запусков можно задать `RUNS` и `WARMUP`, например `RUNS=21 WARMUP=3 scripts/mongo/optimization/run.sh`.

Для каждого этапа записываются медианы `executionTimeMillis`, `totalDocsExamined`, `totalKeysExamined` и `nReturned` (число возвращённых документов), а также отдельные результаты каждого запуска и планировщик с winning plan. Подробные планы сохраняются в `docs/performance/mongo_query_optimization.jsonl`, а сравнительная таблица — в `docs/performance/mongo_query_optimization.md`. Индексы остаются установленными после завершения, в том числе при ошибке замера.

## Результаты

Таблица формируется скриптом из фактических запусков на данных подключённой MongoDB. В текущей базе всего 5 мероприятий, поэтому `executionTimeMillis` может иметь медиану `0` мс; результаты следует интерпретировать по числу просмотренных документов и ключей, количеству возвращённых документов и winning plan.
