# ADR 002: Стратегия версионирования документов MongoDB


## 1. Контекст

В проекте Poster MongoDB используется для хранения дополнительного содержимого мероприятий, информации об исполнителях и отзывов пользователей.

В настоящее время документная модель включает три коллекции:

- `event_pages` — страницы мероприятий;
- `performers` — исполнители, спикеры и театральные труппы;
- `reviews` — отзывы пользователей.

Структура документов определяется JSON Schema-валидаторами, которые создаются скриптом `scripts/mongo/01_schema.js`.

По мере развития приложения структура документов может изменяться. Например, могут появляться новые поля, изменяться типы данных, переименовываться существующие поля или объединяться несколько вложенных объектов.

Изменение структуры без специального механизма версионирования может привести к несовместимости между старой и новой версиями приложения.

Поэтому необходимо определить единый подход к управлению версиями документов MongoDB.

## 2. Принятое решение

Для версионирования документов используется паттерн **Schema Versioning**.

В каждый документ добавляется поле:

`schemaVersion`

Поле содержит целое число, определяющее версию структуры документа.

Пример:

```javascript
{
  _id: 463,
  schemaVersion: 1,
  event: {
    title: "Jazz Festival",
    type: "festival",
    status: "finished"
  }
}
```

Версионирование выполняется независимо для каждой коллекции. Это позволяет изменять структуру одной коллекции без обязательного изменения версий остальных коллекций.

Начальная версия для всех трёх коллекций — `1`.

Документы, созданные до внедрения версионирования и не содержащие `schemaVersion`, считаются документами версии 1 до выполнения первоначального обновления.

## 3. Правила изменения версии

Версия документа увеличивается при несовместимых изменениях структуры.

Изменения, не требующие увеличения версии:

- добавление необязательного поля;
- добавление нового индекса;
- расширение допустимых значений поля без нарушения старой логики;
- добавление необязательных элементов в существующий объект.

Изменения, требующие увеличения версии:

- переименование существующего поля;
- изменение типа данных;
- перенос поля на другой уровень вложенности;
- изменение структуры вложенного объекта;
- удаление поля, которое используется предыдущими версиями приложения;
- изменение обязательности поля таким образом, что старые документы перестают соответствовать новой схеме.

При несовместимом изменении версия увеличивается на единицу.

Например:

- версия 1 — исходная структура;
- версия 2 — изменённая структура;
- версия 3 — следующее несовместимое изменение.

## 4. Обработка документов разных версий

Приложение должно определять структуру документа по значению `schemaVersion`.

Для этого используется слой преобразования документов.

Его задачи:

1. Получить документ из MongoDB.
2. Определить его версию.
3. Проверить, поддерживается ли эта версия приложением.
4. При необходимости преобразовать документ во внутреннюю актуальную модель.
5. Передать нормализованный объект бизнес-логике приложения.

Таким образом, бизнес-логика не должна напрямую зависеть от того, в каком формате документ хранится в MongoDB.

Если поле `schemaVersion` отсутствует, документ временно интерпретируется как версия 1. Такое поведение допустимо только в период первоначального перехода. После завершения первичного обновления все документы должны содержать явную версию.

Если обнаружена неизвестная или неподдерживаемая версия, приложение не должно молча интерпретировать документ как актуальный. Необходимо зафиксировать ошибку и передать её в систему логирования.

## 5. Совместимость при выпуске новой версии

Изменение схемы выполняется поэтапно по принципу Expand – Migrate – Contract.

### Этап 1. Расширение схемы

- Обновляется JSON Schema-валидатор.
- Валидатор временно допускает старую и новую версии документов.
- Существующие документы продолжают успешно проходить проверку.
- Добавляется поддержка чтения обеих версий в приложении.

### Этап 2. Выпуск совместимого приложения

Новая версия приложения должна уметь читать документы старой и новой структуры.

До переключения записи на новую структуру приложение продолжает создавать документы старой версии.

### Этап 3. Переключение записи

После развёртывания совместимого приложения новые и изменяемые документы начинают записываться в новой версии.

При этом чтение старых документов остаётся доступным.

### Этап 4. Обновление старых документов

Запускается отдельная процедура миграции.

Она постепенно преобразует документы старой версии в новую.

### Этап 5. Удаление поддержки старой версии

После проверки, что старых документов больше не осталось:

- удаляется обработка старой версии;
- валидатор перестаёт принимать старую структуру;
- удаляются больше не нужные ветви запросов и преобразований.

## 6. Особенности коллекций Poster

### event_pages

Основная коллекция для применения версионирования.

Содержит снимок основных данных мероприятия из PostgreSQL, описание, программу, типоспецифичные поля, ссылки на исполнителей и кэш рейтинга.

Изменения структуры могут затрагивать вложенные объекты `event`, `details`, `program`, `rating`.

При изменении структуры снимка необходимо сохранять правило владения данными: PostgreSQL остаётся источником истины для основных параметров мероприятия, а MongoDB хранит их копию для чтения.

### performers

Содержит карточки исполнителей и коллективов.

Версионирование применяется независимо от `event_pages`.

Изменение структуры карточки исполнителя не должно требовать миграции страниц мероприятий, если их структура не меняется.

### reviews

Содержит отзывы, оценки и ссылки на мероприятия и пользователей.

Коллекция имеет простую структуру, поэтому изменения здесь ожидаются реже.

Тем не менее она использует тот же механизм `schemaVersion`, чтобы все коллекции проекта следовали единому правилу.

## 7. Требования к миграции

Миграция документов между версиями должна:

- выполняться отдельным скриптом;
- быть идемпотентной — повторный запуск не должен портить уже обновлённые документы;
- выбирать документы по текущей версии;
- обновлять документы небольшими пакетами;
- не изменять данные, владельцем которых является PostgreSQL;
- сохранять идентификаторы `_id` и связи между коллекциями;
- проверять результат обновления;
- фиксировать количество успешно обновлённых и ошибочных документов.

При обновлении одного документа необходимо проверять его текущую версию, чтобы не перезаписать документ, который уже был изменён другим процессом.

## 8. Откат изменений

Откат должен учитывать, были ли уже созданы документы новой версии.

До начала записи документов новой версии можно вернуть предыдущую версию приложения и валидатора.

После появления документов новой версии необходимо использовать один из вариантов:

- обратное преобразование, если оно не приводит к потере данных;
- исправление миграции и повторное преобразование вперёд;
- восстановление из резервной копии, если безопасное обратное преобразование невозможно.

Простое переключение приложения на старую версию без проверки совместимости документов не допускается.

## 9. Проверка корректности

После миграции должны выполняться проверки:

1. Все документы имеют допустимое значение `schemaVersion`.
2. Количество документов до и после миграции совпадает, если миграция не предполагает удаления данных.
3. Обязательные поля соответствуют JSON Schema.
4. Типы данных не изменились некорректно.
5. Ссылки между `event_pages`, `performers` и `reviews` сохраняют целостность.
6. Кэш `event_pages.rating` соответствует данным `reviews`.
7. Снимки мероприятий не нарушают владение данными PostgreSQL.

Для проверки используются существующие сценарии проекта из `scripts/mongo/checks/` и межбазовая сверка PostgreSQL ↔ MongoDB.

Дополнительно должны быть предусмотрены тесты чтения документов старой и новой версии.

## 10. Последствия решения

Преимущества:

- возможность постепенно изменять структуру документов;
- совместимость приложения с несколькими версиями документов;
- отсутствие необходимости одномоментно обновлять всю коллекцию;
- независимое версионирование коллекций;
- контролируемая миграция и возможность восстановления.

Недостатки:

- усложнение логики чтения документов;
- необходимость поддерживать преобразования между версиями;
- временное увеличение сложности JSON Schema-валидаторов;
- необходимость контролировать завершение миграций.

## 11. Реализация в проекте Poster (Sprint 05)

Версии назначаются независимо по коллекциям:

| Коллекция | Текущая версия | Форма документа |
|---|---:|---|
| `event_pages` | 2 | описание хранится в `content.summary` |
| `performers` | 1 | включает исполнителей и труппы |
| `reviews` | 1 | отзывы пользователей |

Seed проставляет `NumberInt(2)` для `event_pages` и `NumberInt(1)` для `performers`, трупп и `reviews`. Валидаторы задаются в `scripts/mongo/01_schema.js`; для `performers` и `reviews` версия обязательна и ограничена BSON `int` со значением 1.

### 11.1. Переход event_pages V1 → V2

В V1 `summary` находится в корне. V2 содержит `schemaVersion: 2`, переносит `summary` в `content.summary` и удаляет корневое поле. Миграция `scripts/mongo/migrations/001_event_pages_v1_to_v2.js` обрабатывает документы без версии и с версией 1, атомарно обновляет документ и защищает запись сравнением версии, `summary` и отсутствия `content`. Повторный запуск не меняет V2 документы. На переходном этапе валидатор принимает legacy V1, явную V1 и V2.

### 11.2. Версии performers и reviews

`scripts/mongo/migrations/002_add_schema_version_to_performers_reviews.js` добавляет только `schemaVersion: NumberInt(1)` документам без поля в обеих коллекциях. Условие обновления проверяет неизменность полного снимка документа. Уже корректная версия пропускается, неожиданное значение или параллельное изменение учитывается как конфликт. Повторный запуск не меняет обработанные документы.

### 11.3. Проверка

`scripts/mongo/migrations/001_verify.js`, запускаемый командой `make mongo-verify`, проверяет наличие BSON `int` с ожидаемым значением во всех документах трёх коллекций. Выводит число документов и несоответствий для каждой коллекции, печатает `RESULT: SUCCESS` или `RESULT: FAILED` и завершает процесс с ненулевым кодом при ошибках. Дополнительные проверки ссылочной целостности и рейтинга находятся в `scripts/mongo/checks/` и `scripts/mongo/cross_check.sh`.

### 11.4. Дальнейшие изменения и обратная совместимость

При несовместимом изменении версии увеличиваются только документы затронутой коллекции. Сначала валидатор и приложение временно принимают обе формы, затем совместимый код переключает запись, выполняется идемпотентная миграция с защитой от конкурентной записи, проверяются результаты, и только после этого убирается поддержка старой формы. Неизвестные версии считаются ошибкой/конфликтом, а не интерпретируются молча. Перед миграцией следует применять валидатор в режиме, совместимом с преобразуемыми документами; строгий целевой валидатор можно включить до миграции, если каждое обновление атомарно приводит документ к целевой схеме.

Проверки и исторические результаты следует фиксировать отдельно; этот ADR описывает реализованные скрипты и команды, но не утверждает, что текущая база была проверена после каждого изменения кода.

### 11.7. Ограничения реализации

- Миграция реализована только для `event_pages`.
- Автоматическое преобразование документов при чтении на уровне приложения пока не реализовано.
- Автоматический обратный переход V2 → V1 не реализован.
- Атомарность обеспечивается для отдельного документа, но не для всей коллекции.
- При конфликте конкурентного изменения документ требует дополнительной проверки.

Общая стратегия версионирования может применяться к `performers` и `reviews` в следующих итерациях проекта.

## 12. Итог

В проекте Poster принимается стратегия версионирования документов через поле `schemaVersion`.

Каждая коллекция получает собственную последовательность версий. Несовместимые изменения структуры сопровождаются увеличением версии и отдельной процедурой миграции.

Переход на новую версию выполняется поэтапно с сохранением совместимости чтения, проверкой целостности и возможностью безопасного отката.

Данное архитектурное решение задаёт основу для последующей реализации миграции документов между версиями схемы MongoDB.
