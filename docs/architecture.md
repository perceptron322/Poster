## Устройство сервиса

Корневой адрес открывает Swagger UI на `/swagger/`. Страница читает `/openapi.yaml`. Go встраивает контракт и статические файлы интерфейса в бинарник во время сборки.

Один процесс Go обслуживает HTTP через `net/http`. Обработчики в `internal/api` отвечают за каталог, учётные записи, публикацию и билеты. Запросы выполняются через `database/sql` и `lib/pq`. Клиент обращается к `/api/v1` с того же origin. Проверка готовности на `/readyz` проверяет PostgreSQL и MongoDB с общим таймаутом две секунды. При недоступной MongoDB готовность и запросы к контенту возвращают 503. Каталог и покупка продолжают работать с PostgreSQL.

PostgreSQL хранит основные поля карточки, справочник площадок, интервалы брони, пользователей, заказы и билеты. Обложка задаётся HTTP(S)-ссылкой. Покупка моделируется внутри сервиса. Расширенные страницы, исполнители и отзывы хранятся в MongoDB 7. Ключ страницы в `event_pages` совпадает с `events.event_id`.

Основа требований — [сценарии первого спринта](sprint-01.md), [модель данных второго спринта](sprint-02.md) и [миграции](../migrations/).

## План и критерии готовности

| Этап | Статус | Реализация и проверка |
| --- | --- | --- |
| 1. Контракт | Готово | OpenAPI описывает запросы, успешные ответы, ошибки, cookie, цены и даты. |
| 2. Запуск и миграции | Готово | `make build` и `make run` собирают и запускают сервис. Миграции применяются и к чистой БД, и поверх прежних таблиц с данными. Повторный запуск пропускает выполненные версии. При отключении БД готовность меняется с 200 на 503. |
| 3. Каталог | Готово | Поиск по буквальной подстроке названия без учёта регистра, тип, диапазон дат, пагинация, карточка с остатком мест, справочник площадок и занятые интервалы. Календарь использует тот же каталог с границами периода, карусель — первые ближайшие события. |
| 4. Вход и роли | Готово | Регистрация создаёт покупателя и сессию. Вход проверяет пароль, выход отзывает текущую сессию. Владелец видит только свои заказы. Организатор может также покупать билеты. |
| 5. Работа организатора | Готово | Публикация или перенос и изменение брони выполняются одной транзакцией. Конфликт расписания даёт 409 и сохраняет прежнюю бронь. После первой продажи можно менять только описание и обложку. |
| 6. Покупка и кабинет | Готово | Заказ и билеты создаются атомарно по цене мероприятия. Два одновременных запроса на последнее место дают один оплаченный заказ и один ответ 409. |
| 7. Возврат и отмена | Готово | При частичном возврате пересчитываются сумма заказа и остаток мест. Полный возврат скрывает заказ из списка. При отмене организатором освобождается площадка, покупатель видит отменённый билет в кабинете. |
| 8. Сквозная проверка | Готово | `make test-api` запускает PostgreSQL 16 и MongoDB 7 в отдельных контейнерах и обращается к запущенному API через HTTP. Команды запуска и примеры приведены в [README](../README.md). |

## Согласованные правила

- **Доступ.** Гость просматривает каталог. Новый пользователь получает роль `customer`. Администратор вручную назначает `organizer` зарегистрированному пользователю. Сессия хранит связь с пользователем, поэтому изменение роли действует со следующего запроса.
- **Учётные данные.** Пароли хешируются PBKDF2-HMAC-SHA256 с индивидуальной случайной солью и 600 000 итераций. Случайный токен сессии передаётся в HttpOnly-cookie со сроком семь дней, в БД хранится его SHA-256. Старые записи из seed сохраняют связи и историю. Для входа нужна учётная запись с паролем.
- **Публикация.** Требуются название, описание, обложка, время начала, длительность, тип, цена и площадка. Интервалы брони полуоткрытые: следующее событие может начинаться в момент окончания предыдущего. Ограничение `ex_bookings_no_overlap` проверяется в самой БД.
- **Продажа.** В заказе от одного до пяти билетов одного мероприятия. В лимите вместимости учитываются билеты `valid` и `used`. Денежные вычисления выполняются в PostgreSQL с типом `numeric`. Клиент может повторить запрос с тем же заголовком `Idempotency-Key` после сетевой ошибки и получить созданный заказ.
- **Возврат.** Клиент отправляет ID выбранных билетов. Перед началом события можно вернуть свои билеты со статусом `valid`. Все запрошенные билеты возвращаются одной транзакцией. После полного возврата заказ получает статус `refunded` и остаётся доступен владельцу по ID.
- **Отмена организатором.** До начала события организатор может его отменить. Опубликованное событие исчезает из каталога, действующие заказы и активные билеты получают `cancelled`, возвращённые сохраняют историю.
- **Одновременные операции.** Покупка, возврат, перенос и отмена начинают изменение с блокировки одной и той же строки мероприятия. Остаток мест и статусы читаются после получения блокировки. Поэтому параллельная покупка не использует устаревший остаток.

## Контент мероприятий

Организатор публикует страницу отдельным `PUT /events/{id}/page` до начала своего мероприятия. Запрос целиком задаёт описание страницы, поля по типу мероприятия, программу, исполнителей и галерею. Перед записью API проверяет владельца в PostgreSQL и ссылки на исполнителей в MongoDB. Форма документа проверяется валидатором коллекции. Запись использует V2 с `content.summary`. Чтение также поддерживает V1 и документы без `schemaVersion`.

Страница и отзывы доступны в архиве завершённых мероприятий. API проверяет статус в PostgreSQL при каждом чтении. После переноса или отмены сервис обновляет совместимый снимок MongoDB после коммита PostgreSQL. При недоступной MongoDB снимок может отстать. Публичный ответ берёт даты и статус из PostgreSQL. При смене типа мероприятия организатор повторно публикует страницу с полями нового типа.

Оплаченный заказ даёт право на один отзыв по мероприятию с опубликованной страницей. Если время окончания опубликованного мероприятия уже прошло, при обращении покупателя для добавления отзыва API фиксирует `finished` в PostgreSQL. Уникальный индекс `(event_id, user_id)` защищает от повторной записи. На standalone MongoDB вставка отзыва и обновление кэша рейтинга — две отдельные записи. Повторный запрос пересчитывает кэш, публичная страница читает рейтинг по фактическим отзывам.

## Маршруты

Пути в таблице приведены относительно `/api/v1`.

| Доступ | Операции |
| --- | --- |
| Публичный каталог | `GET /events`, `GET /events/{id}`, `GET /locations`, `GET /locations/{id}/bookings` |
| Учётная запись | `POST /auth/register`, `POST /auth/login`, `POST /auth/logout`, `GET /me` |
| Покупатель и организатор | `POST /orders`, `GET /me/orders`, `GET /me/orders/{id}`, `POST /me/orders/{id}/refunds` |
| Организатор | `GET /me/events`, `POST /events`, `PATCH /events/{id}`, `POST /events/{id}/cancel` |
| Контент | `GET /performers`, `GET /events/{id}/page`, `PUT /events/{id}/page`, `GET /events/{id}/reviews`, `POST /events/{id}/reviews` |
