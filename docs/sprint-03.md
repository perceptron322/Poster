# scripts/seed — генератор тестовых данных

Детерминированный генератор для PostgreSQL. Один seed → одинаковый
датасет (проверяется через md5). Два режима: `dev` (быстрый) и `load`
(3+ млн строк в `tickets`).

## Проверка транзакций COMMIT и ROLLBACK

Для проверки управления транзакциями в PostgreSQL выполнены два сценария.

### 1. Успешное завершение транзакции — COMMIT

В транзакции выполняется изменение данных. После команды `COMMIT` изменения сохраняются в базе данных и доступны последующим запросам.

### 2. Отмена изменений — ROLLBACK

В отдельной транзакции выполняется изменение данных, после чего вызывается `ROLLBACK`. Изменения отменяются, а база данных возвращается к состоянию до начала этой транзакции.

### Результат

Проверено, что `COMMIT` сохраняет выполненные изменения, а `ROLLBACK` отменяет их. Это подтверждает корректную работу механизмов управления транзакциями PostgreSQL.


## Проверка конкурентных транзакций

Для проверки корректности параллельной покупки билетов реализован сценарий с двумя одновременными транзакциями.

### Цель

Не допустить превышения вместимости площадки при одновременной покупке билетов несколькими пользователями.

### Реализация

Перед покупкой блокируется строка мероприятия с помощью `SELECT ... FOR UPDATE`. Затем система проверяет количество занятых мест. Если свободных мест нет, операция завершается ошибкой.

### Сценарий проверки

1. Создано мероприятие с вместимостью площадки, равной одному месту.
2. В первом подключении начата транзакция покупки билета.
3. Во втором подключении запущена аналогичная операция. Она ожидает освобождения блокировки.
4. После `COMMIT` первой транзакции вторая операция продолжает выполнение и обнаруживает отсутствие свободных мест.
5. Вторая покупка отклоняется, после чего выполняется `ROLLBACK`.

### Результат

Проверка демонстрирует, что при конкурентном выполнении операций успешно проходит только одна покупка. Количество занятых мест остаётся равным вместимости площадки, что предотвращает перепродажу билетов.

### Методика

Для каждого запроса сохранены планы выполнения до и после добавления индексов с помощью `EXPLAIN (ANALYZE, BUFFERS)`.

Использовались следующие индексы:

- `idx_bench_published_datetime` — частичный индекс по дате опубликованных мероприятий с включением дополнительных столбцов.
- `idx_bench_valid_tickets` — частичный индекс по `order_id` для действительных билетов с включением `price`.

```sql
CREATE INDEX idx_bench_published_datetime ON events (datetime)
    INCLUDE (title, ticket_price, location_id, user_id)
    WHERE status = 'published';

CREATE INDEX idx_bench_valid_tickets ON tickets (order_id)
    INCLUDE (price)
    WHERE status = 'valid';
```

### Медианное время выполнения и изменение планов

**Методика.** Скрипт `scripts/optimization/run_median.sh` удаляет индексы, выполняет
`VACUUM ANALYZE` и запускает каждый запрос 3 раза для прогрева (не учитываются) и 15 раз
для замера; затем создаёт индексы, снова выполняет `VACUUM ANALYZE` и повторяет замер.
Учитывается `Execution Time` из `EXPLAIN (ANALYZE, BUFFERS)`. Все данные находятся в
кэше (`shared hit`, чтений с диска нет).

```bash
scripts/optimization/run_median.sh        # RUNS=15 WARMUP=3 по умолчанию
```
(замеры в этом и в прошлом разделе происходили на разных машинах, поэтому отличаются)

| Запрос | Медиана до, мс | Медиана после, мс | Изменение | Разброс до, мс | Разброс после, мс |
|---|---:|---:|---:|---:|---:|
| Каталог мероприятий | 12,258 | 10,481 | **−14,5%** | 11,9–13,1 | 10,3–11,7 |
| Выручка по мероприятиям | 174,721 | 178,889 | +2,4% (в пределах разброса) | 168,2–186,2 | 170,7–186,9 |

#### Каталог мероприятий: `Seq Scan` → `Index Only Scan`

| Узел плана | До | После |
|---|---|---|
| Чтение `events` | `Seq Scan`, фильтр `status = 'published'` отбрасывает 14 575 из 20 000 строк | `Index Only Scan` по `idx_bench_published_datetime`, `Heap Fetches: 0` |
| Буферов на `events` | 352 | 41 |
| Время узла | 2,1 мс | 0,6 мс |
| Буферов на весь запрос | 824 | 513 |

Почему план изменился:

- Индекс **частичный** (`WHERE status = 'published'`): в нём только 5 425 нужных строк,
  поэтому фильтровать ничего не нужно, а сам индекс в 8 раз меньше таблицы.
- Индекс **покрывающий** (`INCLUDE (title, ticket_price, location_id, user_id)`):
  все колонки `events`, которые использует запрос, есть в индексе, поэтому PostgreSQL
  не обращается к таблице (`Heap Fetches: 0` — после `VACUUM` все страницы отмечены
  в карте видимости как полностью видимые).

Почему выигрыш всего 14,5%:

- Чтение `events` занимало лишь ~2 мс из ~12. Основное время уходит на `Seq Scan` по
  `users` (50 000 строк, 468 буферов), два `Hash Join` и сортировку — эти узлы не изменились.
- Узел `Sort` по `datetime` остался, хотя индекс уже упорядочен по дате. В `Hash Join`
  таблица `events` используется для построения хеш-таблицы, а порядок результата
  определяется второй стороной — `users`, поэтому упорядоченность индекса теряется
  и PostgreSQL сортирует 5 425 строк повторно (≈1,5 мс).

#### Выручка по мероприятиям: план не изменился

| Узел плана | До | После |
|---|---|---|
| Чтение `tickets` | `Seq Scan`, фильтр `status = 'valid'`, 2 322 буфера | без изменений |
| Остальные узлы | `Seq Scan` по `orders` и `events`, два `Hash Join`, `HashAggregate`, `Sort` | без изменений |

Почему индекс `idx_bench_valid_tickets` не используется:

- **Низкая селективность условия.** Под `status = 'valid'` попадает 67,3% билетов
  (240 945 из 358 210). Когда запрос читает больше половины таблицы, последовательное
  чтение дешевле обхода индекса: страницы читаются подряд, без переходов по дереву.
- **Оценка стоимости близкая, но в пользу `Seq Scan`.** Индекс меньше таблицы
  (7,4 MB против 18 MB), однако в нём 241 тыс. записей, и стоимость `Index Only Scan`
  оценивается в 7 346 против 6 800 у `Seq Scan`.
- **Чтение билетов — малая часть запроса.** При принудительном отключении
  последовательного чтения (`SET enable_seqscan = off`) PostgreSQL использует индекс:
  `Index Only Scan` занимает 20,8 мс вместо 25,6 мс у `Seq Scan`, но общее время
  остаётся тем же — 178 мс. Основное время (~150 мс) занимают соединение 241 тыс. билетов
  с заказами и мероприятиями, агрегация `HashAggregate` и сортировка, которые индекс
  по `tickets` ускорить не может.

**Вывод.** Индекс для каталога оправдан: запрос стал быстрее на 14,5% и читает на 38%
меньше буферов. Индекс для выручки на этом запросе бесполезен и только увеличивает
стоимость вставки и обновления билетов; запрос агрегирует большую часть таблицы, и
ускорять его имеет смысл другими средствами — например, предрасчётом выручки
(материализованное представление) или сужением выборки по периоду.

## Партицирование таблицы orders: RANGE против HASH

### Цель

Сравнить две стратегии партицирования таблицы `orders` на одинаковой нагрузке
и определить, какая из них лучше подходит для системы.

### Стратегии

| | RANGE | HASH |
|---|---|---|
| Ключ | `created_at` | `user_id` |
| Партиции | по неделе: 9 с данными + 2 впрок + `DEFAULT` = 12 | `MODULUS 8` = 8 |
| Первичный ключ | `(order_id, created_at)` | `(order_id, user_id)` |
| Строк в партиции | от 36 тыс. до 446 тыс. (перекос по датам из генератора) | 171–176 тыс. (равномерно) |
| Размер индексов | 88 MB | 78 MB |

Базовая линия — обычная таблица `orders_plain` (индексы 67 MB). Все три таблицы —
копии `orders` (1 392 503 строки, `make load`, seed 42) с одинаковыми колонками,
ограничениями и индексами по `user_id`, `event_id`, `created_at`. Основная схема
не менялась: в партицированной таблице PK обязан включать ключ партицирования,
поэтому FK `tickets → orders(order_id)` на партицированную таблицу без изменения
схемы невозможен.

### Методика

- PostgreSQL 16 в Docker, 12 CPU, 13 GB RAM, `shared_buffers = 128MB`.
- `pgbench -M prepared -c 8 -j 4 -T 30`, перед каждым замером — прогрев 5 с и `CHECKPOINT`.
- `synchronous_commit = off`: без этого вставки упирались в `fsync` диска хоста,
  и TPS одной и той же таблицы менялся между прогонами в 5 раз.
- Параметры запросов (покупатель, id заказа, день) — случайные, одинаковые диапазоны для всех таблиц.
- Каждый сценарий — один прогон; повторные прогоны дали разброс ±2% для чтений, ±4% для вставки.

| Сценарий | Запрос |
|---|---|
| `by_user` | заказы покупателя: `WHERE user_id = ?` |
| `by_id` | заказ по номеру: `WHERE order_id = ?` |
| `by_period` | выручка за день: `count(*), sum(total_price) WHERE created_at` в пределах суток |
| `insert` | новый заказ, `created_at = now()` |
| `mixed` | смесь: 50% `by_user`, 30% `by_id`, 15% `insert`, 5% `by_period` |

### Результаты: пропускная способность (TPS, больше — лучше)

| Сценарий | Обычная таблица | RANGE (`created_at`) | HASH (`user_id`) |
|---|---:|---:|---:|
| `by_user` | **29 501** | 24 712 (−16%) | 25 024 (−15%) |
| `by_id` | **33 200** | 29 662 (−11%) | 30 211 (−9%) |
| `by_period` | 666 | **1 185 (+78%)** | 679 (+2%) |
| `insert` | 24 097 | 23 962 (−1%) | 24 022 (0%) |

### Выводы

1. **RANGE по `created_at` выигрывает там, где есть фильтр по дате.** Запрос за день читает
   одну партицию (partition pruning) и в 3 раза меньше буферов: в обычной таблице заказы одного
   дня разбросаны по всему файлу, а в партиции лежат рядом. Отсюда +78% на `by_period`.
2. **HASH по `user_id` отсекает лишние партиции, но на текущем объёме это не окупается.**
   Запрос покупателя читает одну партицию из восьми и выполняется быстрее, чем на RANGE,
   но не быстрее обычной таблицы: B-tree по 1,4 млн строк и по 175 тыс. имеет одинаковую глубину,
   а партицирование добавляет накладные расходы (узел `Append`, отсечение партиций при выполнении
   подготовленного запроса, блокировки всех партиций). Выигрыш HASH проявится на объёмах,
   когда индекс перестанет помещаться в память.
3. **Запросы без ключа партицирования дорожают на обеих стратегиях**: `by_id` теряет 9–11% TPS,
   полный проход выполняется на 27–43% дольше, потому что приходится обходить все партиции.
4. **Вставка от партицирования практически не зависит** (разница в пределах погрешности).
5. **Обслуживание — главное практическое преимущество RANGE.** Удаление старых данных —
   `DROP` партиции за миллисекунды вместо `DELETE` на сотни миллисекунд, который ещё и оставляет
   мёртвые строки для `VACUUM`. HASH здесь хуже обычной таблицы.
6. **Итог смешанной нагрузки зависит от доли запросов по периоду**: даже 5% «тяжёлых»
   запросов за день составляют ~70% всего времени, поэтому RANGE даёт +27%, а HASH −8%.

**Рекомендация:** для `orders` подходит **RANGE по `created_at`** — в системе продажи билетов
типичны отчёты за период и архивирование старых заказов. HASH по `user_id` имеет смысл
рассматривать только при росте таблицы на порядки, когда равномерное распределение и
чтение одной партиции на запрос покупателя начнут давать выигрыш.

**Ограничения эксперимента:** данные помещаются в оперативную память, поэтому выигрыш
от чтения меньшего объёма с диска занижен; `pgbench` работает в том же контейнере и
делит с сервером CPU; каждый сценарий измерен одним прогоном.

### Воспроизведение

```bash
cd scripts/seed && make clean load          # ~11 минут
cd ../partitioning
make setup                                  # orders_plain / orders_range / orders_hash + статистика
make explain                                # таблица планов
make bench                                  # pgbench, ~11 минут → results.md
```

Скрипты — в `scripts/partitioning/`: `00_plain.sql`, `01_range.sql`, `02_hash.sql` — создание таблиц,
`10_stats.sql` — размеры и распределение по партициям, `20_explain.sql` — сравнение планов,
`bench/*.sql` — сценарии нагрузки, `run_bench.sh` — запуск.
