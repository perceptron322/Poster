# Sprint 04 — Справочник команд PostgreSQL HA

## 1. Назначение

Этот документ содержит команды для запуска, проверки и демонстрации тестового HA-кластера PostgreSQL в Sprint 04.

Все команды `make` запускаются из корня репозитория Poster.

> **Важно:** перед остановкой узла всегда проверяйте его роль через `make ha-status`. При экспериментах остановка должна соответствовать цели: для проверки отказа реплики остановите реплику, для проверки переключения лидера — текущий primary.

## 2. Основные команды управления

### `make ha-up` — запуск стенда

```bash
make ha-up
```

Запускает компоненты тестового HA-стенда и выполняет предусмотренные скриптом проверки готовности. Используйте перед экспериментами, если стенд остановлен.

### `make ha-status` — состояние кластера

```bash
make ha-status
```

Показывает текущего лидера, реплику и состояние PostgreSQL и репликации. Используйте до и после каждого эксперимента, чтобы определить роли узлов и проверить результат.

### `make ha-test` — автоматические проверки

```bash
make ha-test
```

Проверяет:
1. какой узел является лидером;
2. что второй узел находится в режиме восстановления (`recovery`);
3. что потоковая репликация работает в состоянии `streaming`;
4. что запись на лидере появляется на реплике;
5. что обычная операция записи на реплике отклоняется.

При успешном выполнении ожидается сообщение:

```text
Все тесты пройдены.
```

### `make ha-logs` — логи стенда

```bash
make ha-logs
```

Показывает логи компонентов стенда. Используйте для диагностики проблем запуска, репликации, выбора лидера и маршрутизации HAProxy.

### `make ha-restart` — перезапуск стенда

```bash
make ha-restart
```

Перезапускает стенд согласно логике скрипта управления. После перезапуска проверьте состояние:

```bash
make ha-status
make ha-test
```

### `make ha-down` — остановка стенда

```bash
make ha-down
```

Останавливает компоненты лабораторного стенда, сохраняя данные в именованных томах.

**Не используйте для обычной остановки** `make ha-clean`, `make ha-rebuild` или `docker compose down -v`: эти команды могут удалить данные стенда.

## 3. Команды Docker Compose

В командах ниже используется отдельная конфигурация HA-стенда:

```bash
-f scripts/ha-lab/compose.yaml \
--env-file scripts/ha-lab/.env
```

### Просмотр контейнеров

```bash
docker compose \
  -f scripts/ha-lab/compose.yaml \
  --env-file scripts/ha-lab/.env \
  ps
```

Показывает состояние контейнеров тестового стенда: `patroni1`, `patroni2`, `etcd` и `haproxy`.

### Проверка роли `patroni1`

```bash
docker compose \
  -f scripts/ha-lab/compose.yaml \
  --env-file scripts/ha-lab/.env \
  exec -T patroni1 \
  psql -U course_admin -d course_app \
  -c "SELECT pg_is_in_recovery();"
```

### Проверка роли `patroni2`

```bash
docker compose \
  -f scripts/ha-lab/compose.yaml \
  --env-file scripts/ha-lab/.env \
  exec -T patroni2 \
  psql -U course_admin -d course_app \
  -c "SELECT pg_is_in_recovery();"
```

Результаты обоих запросов интерпретируются так:

- `f` (`false`) — узел является primary;
- `t` (`true`) — узел находится в режиме восстановления и является replica.

В штатном состоянии один узел должен быть primary, а второй — replica.

### Проверка потоковой репликации

Следующая команда предполагает, что `patroni1` сейчас является лидером:

```bash
docker compose \
  -f scripts/ha-lab/compose.yaml \
  --env-file scripts/ha-lab/.env \
  exec -T patroni1 \
  psql -U course_admin -d course_app \
  -c "SELECT application_name, state, sync_state FROM pg_stat_replication;"
```

Если лидером является `patroni2`, замените имя контейнера на `patroni2`.

В поле `state` ожидается значение `streaming`. Если запрос не возвращает строк, проверьте роль узла и доступность реплики.

## 4. Проверка передачи данных

### Создание тестовой таблицы и запись на лидере

Перед выполнением убедитесь через `make ha-status`, что `patroni2` является текущим лидером. Команда создаёт таблицу, если её ещё нет, и добавляет тестовую запись:

```bash
docker compose \
  -f scripts/ha-lab/compose.yaml \
  --env-file scripts/ha-lab/.env \
  exec -T patroni2 \
  psql -U course_admin -d course_app \
  -c "CREATE TABLE IF NOT EXISTS ha_replication_check (
        id SERIAL PRIMARY KEY,
        message TEXT,
        created_at TIMESTAMPTZ DEFAULT NOW()
      );
      INSERT INTO ha_replication_check (message)
      VALUES ('replication test');"
```

Ожидается успешное создание таблицы и вставка строки. Если таблица уже существует, PostgreSQL может вывести `NOTICE` — это нормально.

### Чтение записи на реплике

Если `patroni2` — лидер, а `patroni1` — реплика, выполните:

```bash
docker compose \
  -f scripts/ha-lab/compose.yaml \
  --env-file scripts/ha-lab/.env \
  exec -T patroni1 \
  psql -U course_admin -d course_app \
  -c "SELECT id, message, created_at FROM ha_replication_check ORDER BY id;"
```

Запись, созданная на лидере, должна появиться на реплике. Если роли поменялись, подключайтесь к текущей реплике, а не ориентируйтесь только на имя контейнера.

Идентификаторы `SERIAL` могут иметь пропуски. Это нормально и само по себе не означает потерю строк.

## 5. Эксперимент № 1 — остановка реплики

**Цель:** проверить, продолжает ли лидер принимать записи при временной недоступности реплики и восстанавливается ли репликация после её запуска.

### Шаг 1. Определить роли

```bash
make ha-status
```

Определите, какой узел является лидером, а какой — репликой.

### Шаг 2. Остановить именно реплику

Если репликой является `patroni1`:

```bash
docker compose \
  -f scripts/ha-lab/compose.yaml \
  --env-file scripts/ha-lab/.env \
  stop patroni1
```

Если репликой является `patroni2`, укажите `patroni2` вместо `patroni1`.

### Шаг 3. Проверить состояние

```bash
make ha-status
```

Реплика должна быть недоступна, а лидер — продолжать работу.

### Шаг 4. Добавить запись на лидере

Подключитесь к текущему лидеру и выполните:

```sql
INSERT INTO ha_replication_check (message)
VALUES ('primary works without replica');
```

Ожидается успешная вставка строки. Запрос нужно выполнять именно на лидере.

### Шаг 5. Запустить остановленный узел

Например, если был остановлен `patroni1`:

```bash
docker compose \
  -f scripts/ha-lab/compose.yaml \
  --env-file scripts/ha-lab/.env \
  start patroni1
```

Укажите имя фактически остановленного узла.

### Шаг 6. Проверить восстановление

```bash
make ha-status
make ha-test
```

После восстановления реплика должна подключиться к лидеру и получить изменения.

**Результат ранее проведённого эксперимента:** `patroni1` был остановлен; `patroni2` продолжал принимать записи. После запуска `patroni1` тестовая запись появилась на восстановившейся реплике.

## 6. Эксперимент № 2 — остановка лидера

**Цель:** проверить автоматическое переключение на другой узел после отказа текущего primary.

### Шаг 1. Определить текущего лидера

```bash
make ha-status
```

Не предполагайте, что лидером всегда является один и тот же контейнер.

### Шаг 2. Остановить текущий primary

Если лидером является `patroni2`:

```bash
docker compose \
  -f scripts/ha-lab/compose.yaml \
  --env-file scripts/ha-lab/.env \
  stop patroni2
```

Если лидером является `patroni1`, укажите `patroni1`.

### Шаг 3. Проверить переключение

```bash
make ha-status
```

Если условия переключения выполнены, оставшийся узел должен стать новым лидером.

### Шаг 4. Проверить запись на новом лидере

На новом primary выполните:

```sql
INSERT INTO ha_replication_check (message)
VALUES ('new primary after failover');
```

Ожидается успешная вставка.

### Шаг 5. Запустить остановленный узел

Например, если был остановлен `patroni2`:

```bash
docker compose \
  -f scripts/ha-lab/compose.yaml \
  --env-file scripts/ha-lab/.env \
  start patroni2
```

### Шаг 6. Проверить возвращение узла

```bash
make ha-status
make ha-test
```

Остановленный узел должен вернуться в кластер как реплика, а потоковая репликация — восстановиться.

**Результат ранее проведённого эксперимента:** после остановки `patroni2` лидером стал `patroni1`. После повторного запуска `patroni2` вернулся как реплика; проверенные записи присутствовали на восстановившемся узле.

## 7. Проверка маршрутизации HAProxy

### Подключение для записи

Команда выполняется из контейнера `patroni1` и проверяет, на какой сервер HAProxy направляет подключение для записи:

```bash
docker compose \
  -f scripts/ha-lab/compose.yaml \
  --env-file scripts/ha-lab/.env \
  exec -T patroni1 \
  psql "host=haproxy port=5432 user=course_admin dbname=course_app" \
  -c "SELECT inet_server_addr(), pg_is_in_recovery();"
```

Интерпретация результата:

- `pg_is_in_recovery() = f` — подключение обслуживает primary;
- `pg_is_in_recovery() = t` — подключение обслуживает replica.

После переключения лидера повторите запрос, чтобы проверить маршрутизацию нового подключения.

### Подключение для чтения

Точка чтения на хосте: `127.0.0.1:55433`.

```bash
psql "host=127.0.0.1 port=55433 user=course_admin dbname=course_app" \
  -c "SELECT inet_server_addr(), pg_is_in_recovery();"
```

Команда предполагает, что клиент `psql` установлен на хосте, порт опубликован и аутентификация настроена. Для реплики ожидается `pg_is_in_recovery() = t`. Если подключение не удалось, проверьте опубликованные порты, конфигурацию HAProxy и логи. Не считайте проверку успешной без результата запроса.

## 9. Рекомендуемый порядок демонстрации

| Шаг | Команда или действие | Что демонстрируется |
|---|---|---|
| 1 | `make ha-up` | Запуск тестового стенда |
| 2 | `make ha-status` | Текущее состояние и роли узлов |
| 3 | `make ha-test` | Автоматические проверки |
| 4 | Проверить `pg_is_in_recovery()` на обоих узлах | Различие primary и replica |
| 5 | Записать строку на лидере и прочитать её на реплике | Потоковая репликация |
| 6 | Остановить реплику и проверить запись на лидере | Работа при недоступности реплики |
| 7 | Запустить реплику, выполнить `make ha-status` и `make ha-test` | Восстановление репликации |
| 8 | Остановить текущего лидера | Отказ основного узла |
| 9 | Выполнить `make ha-status` | Переключение лидера |
| 10 | Записать строку на новом лидере | Запись после переключения |
| 11 | Запустить остановленный узел и выполнить `make ha-test` | Возвращение узла в кластер |
| 12 | Выполнить проверку через HAProxy | Маршрутизация к текущему лидеру |

Для демонстрации сначала покажите состояние кластера и автоматические тесты, затем объясните два эксперимента с остановкой узлов. Повторное проведение экспериментов выполняйте только при наличии времени и возможности безопасно восстановить стенд.

## 10. Меры предосторожности

- Все команды `make` запускайте из корня репозитория.
- Перед остановкой узла выполняйте `make ha-status`.
- Для эксперимента с отказом реплики останавливайте именно реплику.
- Для эксперимента с переключением останавливайте именно текущий primary.
- Не используйте `make ha-clean`, `make ha-rebuild` или `docker compose down -v` для обычной остановки: они могут удалить данные лабораторного стенда.
- Не останавливайте и не изменяйте отдельный контейнер основной базы приложения `poster-db`.
- Не публикуйте содержимое `scripts/ha-lab/.env`, пароли и другие секреты.
- После экспериментов убедитесь, что оба узла доступны, один является лидером, второй — репликой, а `make ha-test` завершается успешно.

## 11. Итог

Эта памятка позволяет запускать тестовый HA-стенд, проверять роли узлов и потоковую репликацию, проводить эксперименты с остановкой реплики и лидера, проверять восстановление кластера и маршрутизацию HAProxy. Успешный результат подтверждается состоянием `streaming` и прохождением автоматических тестов.
