## 2. Что было реализовано

С использованием официального драйвера Go (`go.mongodb.org/mongo-driver`) реализована функция пакетной обработки `ProcessReviewsBatch`, которая выполняет два типа операций над разными коллекциями:

- **Вставка отзывов** (`InsertOne`) в коллекцию `reviews`.
- **Атомарное обновление** счётчика отзывов (`$inc`) и метки времени (`$set`) в коллекции `event_pages`.

Дополнительно реализована защита от «раздувания» счётчиков: обновление `rating.count` выполняется только для тех мероприятий, чьи отзывы реально были вставлены в базу. Для этого индексы неудачных операций собираются из `BulkWriteException`, и по ним исключаются соответствующие обновления мероприятий.

## 3. Обоснование выбора режима `unordered` (`SetOrdered(false)`)

В настройках запроса явно указан режим `SetOrdered(false)`. Это решение обосновано двумя причинами:

- **Производительность.** Драйвер может выполнять операции параллельно, что даёт значительный прирост скорости при работе с большими объёмами данных.
- **Отказоустойчивость.** При массовой загрузке отдельные записи могут быть некорректными (дубликаты или нарушение схемы). В режиме `unordered` ошибка в одной операции не прерывает весь пакет: корректные данные сохраняются, а проблемные — изолированы. В режиме `ordered` первая же ошибка отменила бы все последующие операции.

## 4. Обработка частичных ошибок

Вместо аварийного завершения программы реализован перехват исключения `mongo.BulkWriteException`. Код анализирует массив ошибок (`WriteErrors`), определяет тип проблемы по коду и логирует её, позволяя пакету завершиться успешно для валидных данных:

| Код ошибки | Тип ошибки | Описание | Реакция системы |
| --- | --- | --- | --- |
| `11000` | `duplicate key error` | Попытка добавить отзыв от пользователя, который уже оставлял отзыв для этого мероприятия (нарушение уникального индекса `one_review_per_user`) | Ошибка фиксируется в логах, операция пропускается; счётчик мероприятия не увеличивается |
| `121` | `Document failed validation` | Данные нарушают правила JSON Schema (например, рейтинг больше 5) | Ошибка фиксируется в логах, операция пропускается; счётчик мероприятия не увеличивается |

Такой подход обеспечивает устойчивость к частичным сбоям и прозрачность: по логам сразу видно, какие именно записи не прошли обработку и по какой причине.

### 5. Обеспечение согласованности данных (Consistency)
При использовании режима `unordered` существует риск рассинхронизации: если вставка отзыва (`InsertOne`) завершится ошибкой (например, из-за валидации), парное обновление счётчика (`UpdateOne`) в плоском пакете всё равно бы выполнилось. 

Для решения этой проблемы реализован **двухпроходный подход (Two-Pass Approach)**:
1. **Проход 1:** Выполняется пакетная вставка всех отзывов. В случае `mongo.BulkWriteException` система анализирует массив `WriteErrors` и запоминает индексы неудачных операций (`failedInsertIndices`).
2. **Проход 2:** Формируется и выполняется пакет обновлений `$inc` **только для тех элементов**, индексы которых отсутствуют в `failedInsertIndices`. 

Это гарантирует, что `event_pages.rating.count` всегда точно отражает реальное количество документов в коллекции `reviews`. Кроме того, функция возвращает ошибку (`%w`) вызывающему коду при частичном сбое, предотвращая маскирование критических инцидентов.

## 6. Транзакция MongoDB и гарантии согласованности

### Сценарий

Добавление отзыва меняет две коллекции: документ вставляется в `reviews`, после чего из отзывов мероприятия пересчитывается кэш `event_pages.rating`. Обе операции выполняются одной транзакцией Replica Set. Если обновление кэша не проходит, вставка отзыва откатывается.

Запускать сценарий нужно на Replica Set из `docker-compose.mongo-rs.yml`:

```bash
docker compose -f docker-compose.mongo-rs.yml up -d --wait
make mongo-transaction-demo SCENARIO=all
```

Доступны отдельные сценарии `success`, `rollback` и `retry`. `all` выполняет их последовательно. Runner использует изолированную БД `poster_tx_demo` с тестовыми `event_pages` и `reviews`; она пересоздаётся и удаляется после сценариев, поэтому данные приложения не меняются.

В сценарии `rollback` после вставки отзыва возвращается обычная ошибка. Проверка подтверждает, что транзакция не оставила ни отзыв, ни изменение рейтинга. `retry` проверяет повтор callback с инъецированной временной меткой. Для ошибки, возвращённой самим MongoDB, используйте отдельный тестовый Replica Set:

```bash
make mongo-transaction-server-retry
```

Этот сценарий запускает изолированные MongoDB-узлы с включёнными test commands, на один `update` применяет `failCommand` с `WriteConflict` и меткой `TransientTransactionError`, затем проверяет повтор транзакции и удаляет тестовые Docker volumes. Основной Replica Set и его конфигурация не меняются.

### Выбранные гарантии

| Параметр | Выбор | Влияние в сценарии |
| --- | --- | --- |
| `readConcern` | `snapshot` внутри транзакции; `majority` для обычных чтений | Транзакция читает согласованный снимок `reviews`; обычные чтения не видят данные, не подтверждённые большинством. |
| `writeConcern` | `majority` | Успешный commit подтверждён большинством участников Replica Set, поэтому отзыв и его рейтинг устойчивее к отказу одного узла. |
| `readPreference` | `primary` | Отзыв и рейтинг читаются с актуального Primary; чтение не уходит на отстающий Secondary. Цена — чтения концентрируются на Primary. |

Для транзакций MongoDB используется `primary` read preference. Драйвер задаёт snapshot и majority на параметрах транзакции, а настройки клиента для вне-транзакционных операций — majority/primary.
