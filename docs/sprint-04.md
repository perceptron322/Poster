## Секреты

- Реальные значения паролей и ключей хранятся только в `.env`, который в `.gitignore`
  (там же `*.key`, `*.pem`, `*.crt`, `.pgpass`, `secrets/`).
  В репозитории лежит лишь шаблон `.env.example` с заглушками `change_me*`.
- `make env` (и `make ha-lab-env` для `scripts/ha-lab`) создаёт `.env` с правами `600`
  или дописывает в него недостающие переменные; каждая заглушка заменяется
  своим случайным значением (`openssl rand -hex 16`), уже заданные значения не меняются.
- Makefile читает только `.env`, заглушки из шаблона не подставляются: без нужной
  переменной `migrate` и `create-roles` падают с понятной ошибкой.
- Пароль `secret`, который был в ранних коммитах (`.env.example`, `seed/config*.json`,
  `Makefile`, `README`), считается скомпрометированным и нигде не используется.
  Эти коммиты перечислены в `.gitleaksignore`, историю не переписываем.
- В CI секреты берутся из GitHub → Settings → Secrets and variables → Actions,
  на сервере — из `.env` с правами `600` или Docker secrets.
- Перед коммитом проверка `gitleaks` (`make secrets-scan`, pre-commit хук, CI).
- Если секрет попал в git — сначала сменить его, потом уже чистить историю.

## Резервное копирование и восстановление

Логический бэкап (`pg_dump`) базы `poster` и восстановление в отдельный чистый экземпляр
PostgreSQL 16 (сервис `restore` в `docker-compose.yml`, профиль `restore`, порт `5435`).

```bash
make backup                 # роли + база -> backups/poster_<дата>.{roles.sql,dump,sha256}
make restore                # самый свежий бэкап -> чистый экземпляр + сверка с исходной БД
make restore file=backups/poster_20261019_235104.dump   # конкретный бэкап
make restore-down           # удалить экземпляр восстановления
```

Что делают скрипты (`scripts/backup/`):

1. `backup.sh` — `pg_dumpall --roles-only` (роли с хешами паролей: без них не восстановятся
   права `GRANT`) и `pg_dump -Fc`; файлы пишутся через `.tmp`, чтобы при сбое не остался
   обрезанный бэкап; считаются `sha256`; архив проверяется `pg_restore --list`.
2. `restore.sh` — проверяет контрольные суммы, пересоздаёт контейнер `restore` с пустым
   томом и убеждается, что базы `poster` в нём нет; восстанавливает роли, затем базу
   (`pg_restore -C --exit-on-error`).
3. `compare.sql` выполняется на исходной и восстановленной БД, результаты сравниваются `diff`:
   число строк и md5 содержимого каждой таблицы, ограничения, индексы, расширения,
   значения последовательностей, роли и права на таблицы.

Бэкапы содержат персональные данные и хеши паролей: `backups/` в `.gitignore`,
файлы создаются с правами `600`.

 Репликация PostgreSQL: тестовый HA-стенд

## 1. Цель работы

Цель работы — развернуть тестовый кластер PostgreSQL с механизмом высокой доступности (High Availability, HA), проверить потоковую репликацию между узлами, исследовать поведение кластера при остановке реплики и основного узла, а также убедиться в восстановлении репликации после возвращения узлов в работу.

В рамках работы проверялись:
- запуск двух узлов PostgreSQL;
- определение ролей primary и replica;
- передача изменений от основного узла к реплике;
- возможность записи при недоступности реплики;
- автоматическое переключение лидера при остановке основного узла;
- возвращение остановленного узла в кластер;
- маршрутизация подключений через HAProxy;
- автоматические проверки состояния кластера.

## 2. Архитектура тестового стенда

Учебный стенд расположен в каталоге `scripts/ha-lab/` и использует Docker Compose для запуска необходимых компонентов.

В состав стенда входят:

| Компонент | Назначение |
|---|---|
| `patroni1` | Первый узел PostgreSQL |
| `patroni2` | Второй узел PostgreSQL |
| `etcd` | Хранение состояния кластера и координация работы Patroni |
| `haproxy` | Маршрутизация клиентских подключений к узлам PostgreSQL |

Узлы PostgreSQL работают под управлением Patroni 4.1.5 и используют PostgreSQL 17. Роли узлов динамические: каждый узел может стать лидером или репликой в зависимости от состояния кластера и результатов выборов лидера.

**Primary (лидер)** принимает запросы на запись и передаёт изменения реплике.

**Replica (реплика)** получает изменения посредством потоковой репликации PostgreSQL. В штатном режиме реплика находится в режиме восстановления и не принимает обычные операции записи.

**etcd** хранит информацию, необходимую Patroni для координации состояния кластера и определения текущего лидера.

**HAProxy** предоставляет клиентам точки подключения, позволяющие направлять запросы на запись к текущему лидеру, а запросы на чтение — к реплике.

Стенд использует отдельные контейнеры, сеть Docker и именованные тома. Он предназначен для лабораторного тестирования и изолирован от основной базы данных приложения Poster.

Основные файлы конфигурации:
- `scripts/ha-lab/compose.yaml` — описание контейнеров и сетевой конфигурации;
- `scripts/ha-lab/patroni/` — конфигурация Patroni;
- `scripts/ha-lab/ha.sh` — скрипт управления и проверки состояния стенда.

## 3. Запуск и проверка репликации

### 3.1. Запуск стенда

Для запуска стенда предусмотрена команда:

```bash
make ha-up
```

Для проверки текущего состояния кластера используется:

```bash
make ha-status
```

Команда отображает текущего лидера, реплику и состояние репликации.

В ходе экспериментов роли узлов изменялись. В одном из проверенных состояний `patroni2` являлся лидером, а `patroni1` — репликой. После тестирования отказоустойчивости кластер перешёл в другое состояние: лидером стал `patroni1`, а `patroni2` — репликой.

Это подтверждает, что роли узлов не закреплены за конкретными контейнерами и могут изменяться при переключении лидера.

### 3.2. Проверка потоковой репликации

Для проверки передачи данных была создана тестовая таблица `ha_replication_check` с полями:
- `id` — идентификатор записи;
- `message` — текст сообщения;
- `created_at` — время создания записи.

На текущем лидере была создана таблица и добавлена тестовая запись.

Затем данные проверили на втором узле. Тестовая запись присутствовала на реплике, что подтвердило передачу изменений посредством потоковой репликации.

Дополнительно проверялось состояние соединения между узлами. Реплика находилась в состоянии `streaming`, то есть получала поток изменений от лидера.

Для определения роли PostgreSQL использовался запрос:

```sql
SELECT pg_is_in_recovery();
```

Результат `false` означает, что узел работает как основной сервер, а `true` — что узел находится в режиме восстановления и работает как реплика.

Для проверки состояния соединения репликации на основном узле использовался запрос:

```sql
SELECT
    application_name,
    state,
    sync_state
FROM pg_stat_replication;
```

Ожидаемое состояние работающей реплики — `streaming`.

**Результат:** потоковая репликация между двумя узлами работает, а изменения, внесённые на лидере, передаются на реплику.

|---|---|
| `127.0.0.1:55432` | Подключение для записи через HAProxy |

Это подтвердило, что проверенное соединение обслуживалось лидером.

Проверка выполнена после переключения ролей, когда лидером являлся `patroni1`.

**Вывод:** маршрутизация подключения для записи через HAProxy направляла запрос на текущий лидер. Отдельное полноценное тестирование всех сценариев маршрутизации для чтения в рамках этой проверки не проводилось.

## 9. Ограничения стенда

Стенд предназначен для учебного тестирования и не является полноценной промышленной конфигурацией высокой доступности.

Основные ограничения:

1. **Единственный экземпляр etcd.** При отказе единственного экземпляра etcd могут возникнуть проблемы с координацией кластера и определением лидера.
2. **Асинхронная репликация.** При аварийном отказе основного узла последние подтверждённые клиенту изменения не во всех сценариях гарантированно окажутся на реплике.
3. **Проверенные сценарии отказа ограничены.** Эксперименты подтверждают работоспособность конкретных сценариев остановки и восстановления узлов, но не доказывают устойчивость к любым сетевым разделениям, аппаратным сбоям и одновременным отказам компонентов.
4. **Проверка приложения не выполнялась.** В рамках работы проверялись PostgreSQL, Patroni, etcd, HAProxy и передача данных. Поведение HTTP-приложения Poster во время переключения лидера отдельно не подтверждалось.
